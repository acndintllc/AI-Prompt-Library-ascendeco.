PART 7: CODING PARTNERS vs. REACTIVE ASSISTANTS
================================================================================

7.1 THE CRITICAL DISTINCTION

7.1.1 Coding Assistant (Chatbot-Style / Codex)
  - Reactive (waits for prompt)
  - Limited scope (single file or function)
  - Low autonomy (needs constant approval)
  - Limited context (open file only)
  - Best for: boilerplate, syntax, in-flow help

7.1.2 AI Agent (Terminal-Based / Agentic)
  - Proactive (plans and executes)
  - Repository-wide scope (system understanding)
  - High autonomy (multi-step workflows)
  - Deep codebase understanding
  - Best for: refactors, migrations, debugging, CI/CD

7.2 WHY CODING PARTNERS ARE SUPERIOR

7.2.1 Context-Persistence
  - Lives in repository
  - Understands project conventions, naming, architecture
  - Vastly superior context vs. web chat

7.2.2 Execution Loop (Plan-Act-Verify)
  - Autonomous iteration
  - Reads error logs, identifies issues, retries
  - Does not require user to fix failures

7.2.3 Tool Authority (Permission Levels)
  - Suggest (advice only)
  - Auto-Edit (modify single files)
  - Full Auto (full repository control)
  - Graduated permission system enables delegation

7.3 2026 LANDSCAPE

7.3.1 Terminal-Based AI Agents
  - Claude Code
  - Codex CLI
  - Operate in local development environment
  - Can read entire repository, execute commands, run tests
  - Current gold standard for coding partners

7.3.2 Convergence Reality
  - Agentic CLIs blur line between "coding tool" and "autonomous agent"
  - Most mature teams use both: assistants for fast-paced in-IDE coding + agents for long-running complex tasks

PART 8: PLATFORM DYNAMICS, BIAS & DEFENSE
================================================================================

8.1 AI BIAS: INPUT-TO-OUTCOME DISTORTION

8.1.1 Where Bias Enters the System
  - Input Bias (biased training data replicating historical prejudice)
  - System (Design) Bias (introduced during development, feature prioritization)
  - Application (Deployment) Bias (emerges in real-world use, concept drift)
  - The "Black Box" Problem (opaque decision-making undermines accountability)

8.2 PLATFORM-CENTRIC DISTORTION

8.2.1 Architectural Self-Preference (The "Best-Self" Bias)
  - AI inherently promotes platform's ecosystem/partners
  - Optimization-Driven Bias (fine-tuned to maximize engagement within walled garden)
  - The "Challenge" Requirement (platforms don't include self-conflict disclaimers)

8.2.2 The "Sycophancy" Feedback Loop
  - AI provides answers aligning with user's preferences, not objective truth
  - Model learns that confirming biases = high-engagement interaction
  - Creates loop where AI confirms biases instead of challenging

8.3 CHALLENGE-RESPONSE FRAMEWORK FOR USERS

8.3.1 Information Interrogation
  - Treat AI output as draft/hypothesis, not fact

8.3.2 The "Double-Blind" Challenge
  Step 1: Initial Query ("What is the best CRM for media studio?")
  Step 2: Challenge ("Provide three arguments against top option")
  Step 3: Constraint ("Re-evaluate without platform X's products")

8.3.3 Detecting Platform Bias
  - If answer changes drastically when stripping platform options = bias exposed

8.4 KEY TERMS FOR GLOSSARY

8.4.1 Bias Definitions
  - Platform-Centric Distortion (output skewed toward platform partners)
  - Sycophancy Bias (AI affirms existing biases for engagement)
  - Adversarial Querying (intentionally challenging to expose bias)
  - Out-of-Band Verification (verifying via independent third-party sources)

8.5 THE NEUTRALITY MYTH (Framing for Book)

"In 2026, the 'Neutral AI' is a myth. Every model carries the fingerprints of its creators and commercial partners. To avoid becoming an AI slave, shift from Information Consumption to Information Interrogation. If AI says a platform is 'the best,' challenge the criteria and demand landscape view excluding platform's interests."

9.4 THE "TRANSPARENCY STACK"

9.4.1 Chain of Trust Workflow
  Step 1: Creation (AI applies Signature/SynthID at generation)
  Step 2: Storage (Provenance recorded, every edit tracked)
  Step 3: Verification (User checks digital signature against ledger)
  Step 4: Disclosure (If no signature, mark as "Unverified" or "Potentially Synthetic")

9.5 THE VERIFICATION GAP

9.5.1 Critical Gap Concept
